# Selective NSD + GRPO — учебный проект

**Четыре эксперимента на `Qwen/Qwen3-1.7B` и MATH:**

| Эксперимент | Обучение |
|---|---|
| `baseline` | нет, только оценка исходной модели |
| `grpo` | обычный GRPO |
| `grpo_nsd_all` | GRPO + NSD на всех генерациях |
| `grpo_nsd_zero` | GRPO + NSD только в группах, где все ответы ошибочные |

**Как запускать (установка, смоук-тест, боевой прогон, прерывания): см. [`RUNBOOK.md`](RUNBOOK.md).** Коротко:

```bash
pip install -r requirements.txt && python -m pytest -q
scripts/smoke.sh                              # 10 шагов + проверка resume, ~20–30 мин
PROFILE=short SEEDS="1" scripts/run_all.sh    # все 4 эксперимента, сводка в results/runs/short/summary.md
```

Нужны 2 GPU с bf16 (Ampere или новее): на одной vLLM генерирует ответы, на другой идёт обучение.

## Где менять параметры

- `configs/common.yaml` — общие гиперпараметры **для всех методов**: модель, LoRA, LR, длины, NSD λ/α, vLLM, настройки eval. Методы различаются только полем `experiment` в `configs/<experiment>.yaml`, тест `tests/test_config.py` это проверяет.
- `configs/profiles/{short,full,smoke}.yaml` — бюджет: задач на шаг, число шагов, размер eval.
- Разовая подмена любого поля из CLI: `python -m src.experiment ... --set key=value`.

`thinking: false` фиксирует non-thinking режим Qwen3. Нельзя менять его между экспериментами. `temperature=1.0` при обучении зафиксирована в коде, чтобы NSD использовал исходные (а не изменённые температурой) вероятности токенов. Ещё `top_p: 1.0`: так сэмплирование идёт из той же полной вероятностной модели, на которой считается loss.

## Архитектура

- `src/config.py`: сборка конфига (эксперимент → `common.yaml` → профили → `--set`), производные поля, путь запуска `results/runs/<profile>/<experiment>_s<seed>/`.
- `src/data.py`: весь MATH train (7 категорий) и **непересекающийся MATH-500 test**. В prompt предусмотрен формат `Answer: \\boxed{...}`.
- `src/rewards.py`: бинарная награда по **финальному** ответу. `math-verify` используется для математической эквивалентности; следует вручную аудировать ошибки verifier.
- `src/trainer.py`: расширение `trl==0.24.0` `GRPOTrainer`, сохраняющее GRPO loss и добавляющее NSD auxiliary loss.
- `src/nsd.py`: paper-inspired gating и bounded unlikelihood + pointwise KL, выбор генераций `all`/`zero`.
- `src/experiment.py`: обучение (генерация через `trl vllm-serve`, LoRA в bf16, чекпоинты и автоматический resume, замер времени каждого шага) и запуск eval.
- `src/evaluation.py`: одинаковая оценка на всём MATH-500 через vLLM: greedy accuracy, Avg@8, Pass@8, доля обрезанных ответов.
- `src/plots.py`: сводная таблица по seeds, парные сравнения методов на одних и тех же задачах с 95% CI, кривые обучения, отчёт смоук-теста.
- `scripts/run_all.sh`, `scripts/smoke.sh`: оркестрация vLLM-сервера, обучения и оценки.
- `notebooks/results.ipynb`: просмотр результатов и аудит verifier. Старые ноутбуки под одну GPU лежат в `notebooks/legacy/`.

### Что именно означает `Zero`

Для группы генераций (по умолчанию 8) с binary rewards `r=[0,…,0]` включаем NSD **на всех генерациях группы**. Группа `[1,…,1]` не считается ошибочной, хотя её относительный advantage тоже нулевой.

`All` и `Zero` используют одинаковый `nsd_lambda` и `nsd_alpha`. Дополнительный loss усредняется **по всему микро-батчу**, включая невыбранные нулевые слагаемые: это сохраняет сопоставимый масштаб каждой активной генерации между режимами. NSD loss **не нормируется по числу активных генераций**.

### Важные отличия от оригинальной статьи NSD

1. В основном алгоритме Pei et al. negative condition генерируется самой моделью online. Здесь применяется **offline фиксированный вопросно-тематический шаблон** (`src/data.py`) для экономии времени/ресурсов. Это упрощённая исследовательская реализация, а не точная репликация оригинального метода.
2. Teacher и reference используют **исходную замороженную базовую модель**: во время forward отключаем LoRA-адаптер, а не храним 2 дополнительные полные копии модели.
3. Гибрид `GRPO + λ * NSD` — предложенная для учебной работы интеграция, не оригинальный алгоритм авторов NSD.
4. Это **proof of concept на 2 GPU** (одна генерирует, одна учит), основанный на внутреннем API конкретной версии TRL, а не готовая распределённая промышленная система. Обучается LoRA, а не все веса модели.
5. Оценка: Avg@8 на всём MATH-500 (`temperature=0.6`, `top_p=0.95`, до 2048 токенов) плюс greedy. Для выводов смотрите парные сравнения с CI в `summary.md` и повторяйте запуски с разными seeds.
6. `grpo_beta` активирует регуляризацию GRPO, а `nsd_alpha` — дополнительный KL-компонент NSD. Различие в регуляризации может стать смешивающим фактором; KL-only контроль и сопоставление вычислительных бюджетов нужны для углублённой работы.

## Как оценивать результаты честно

Модель, датасет, длины, sampling и бюджет по optimizer steps общие для всех методов (`configs/common.yaml` + профиль). В анализе указывайте, что hybrid запускает дополнительные forward passes, поэтому сравнивайте **и по времени/GPU-часам**, а не только по числу шагов. Доля обрезанных ответов пишется и в eval (`truncated_fraction`), и в логах обучения (`completions/clipped_ratio`): если она велика, accuracy занижена из-за обрывов генераций.

## Работа команды

- Участник 1: сервер, `src/experiment.py`, `scripts/*.sh`, смоук-тест, CUDA/OOM, запуск прогонов.
- Участник 2: `src/nsd.py`, `src/trainer.py`, тесты routing, контроль `nsd/*` метрик в логах.
- Участник 3: `src/data.py`, `src/rewards.py`, `src/evaluation.py`, аудит verifier в `notebooks/results.ipynb`, графики и отчёт.
