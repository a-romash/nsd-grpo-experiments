# Выбор сервера (Selectel, прерываемый)

Короткий ответ: хватит **1× A100**. Если хотите погонять эксперименты параллельно, берите **2× A100**. T4 не берите. Почему так, видно из кода:

## Что в коде определяет выбор

- **Только одна GPU на процесс.** `src/experiment.py:43` падает, если видно больше одной GPU, а NSD-тренер дополнительно проверяет `num_processes == 1`. Распределённого обучения нет, поэтому несколько карт дают только запуск разных экспериментов одновременно, по одному на карту через `CUDA_VISIBLE_DEVICES=0`, `=1` и т.д.
- **Задача маленькая.** Модель Qwen3-1.7B в 4-bit QLoRA, LoRA r=8, ответы до 384 токенов, 24 шага, eval на 100 задачах. В A100 40GB это помещается с большим запасом.
- **Всего 4 запуска:** baseline (только eval) и 3 обучения. 8 карт занять просто нечем.

## Почему не T4

- **Нет bf16.** Код автоматически перейдёт на fp16 (`src/experiment.py:55,78`). Для GRPO и NSD, где считаются logprob и KL, fp16 рискованнее: возможны переполнения и NaN в loss. README при этом рассчитан на bf16.
- **Не проверено.** README прямо пишет, что 16 ГБ «могут оказаться достаточными… но это не проверено».
- **Медленно.** Генерация через HF `generate` (vLLM выключен) упирается в пропускную способность памяти: у T4 ~320 ГБ/с, у A100 ~1.5–2 ТБ/с. Каждая отдельная тренировка на T4 будет в разы дольше, и количество карт этого не исправит.

## Варианты

1. **1× A100 40/80GB.** Оптимум. Все 4 запуска идут по очереди. На пилотных настройках, по грубой оценке, это порядка 2–4 часов на всё вместе с eval (не замерялось).
2. **2× A100.** Если важно время или будете увеличивать `max_steps`. Схема: GPU0 гоняет `grpo`, потом `grpo_nsd_zero`; GPU1 гоняет `baseline`, потом `grpo_nsd_all`. Wall-clock каждого запуска при этом остаётся честным, потому что карты не делятся.
3. **Дешевле, если у Selectel есть в наличии:** любая Ampere-карта или новее с 24+ ГБ (L4, A10, A30, A5000, RTX 4090). Там есть bf16 и памяти хватает. Для этого объёма работы это лучший вариант по цене и качеству.

Пример запуска на 2 GPU:

```bash
CUDA_VISIBLE_DEVICES=0 python -m src.experiment --config configs/grpo.yaml
CUDA_VISIBLE_DEVICES=1 python -m src.experiment --config configs/baseline.yaml
```

## Остальные ресурсы (на один сервер)

| Ресурс | Сколько | Комментарий |
|---|---|---|
| vCPU | 8 (на 2 GPU 12–16) | CPU почти не нагружается, `dataloader_num_workers=0` |
| RAM | 32 ГБ (на 2 GPU 48–64) | загрузка модели и датасетов, запас для Jupyter |
| Облачный диск | **50 ГБ**, со 100 ГБ можно не думать | см. расчёт ниже |
| Локальный/загрузочный | 20–30 ГБ под ОС | всё рабочее держать на облачном диске |

**Что займёт место на облачном диске:**

- venv с PyTorch CUDA и зависимостями: ~8–10 ГБ;
- HF-кэш: Qwen3-1.7B ~3.5 ГБ, MATH и MATH-500 меньше 0.5 ГБ;
- LoRA-адаптеры: десятки МБ каждый; метрики и графики: копейки;
- **итого ~15 ГБ.** 50 ГБ хватит с запасом, 100 ГБ стоит брать, если позже решите пробовать модели крупнее.

Чтобы всё лежало на облачном диске, смонтируйте его, например, в `/data` и пропишите:

```bash
export HF_HOME=/data/hf_cache
# репо и .venv держать в /data/nsd_grpo_starter
```

## Важно для прерываемого сервера

В `src/experiment.py:81` стоит `save_strategy="no"`, а адаптер сохраняется только в конце (`trainer.save_model`). Если сервер прервут посреди обучения, этот запуск потеряется целиком.

- На пилоте (24 шага, десятки минут на запуск) это терпимо: просто перезапустить.
- Если увеличите `max_steps`, нужно включить `save_strategy="steps"` с `save_steps` и добавить `resume_from_checkpoint`.

Ещё одно: уточните в документации Selectel, что происходит с прерываемым сервером. Если при прерывании удаляется загрузочный диск, всё, что на нём лежало, пропадёт. Отдельный облачный том при этом, как правило, сохраняется, поэтому кэш, venv и `results/` лучше держать на нём.
